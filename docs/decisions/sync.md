# Sync

Decisions from the 2026-10-24 investigation ([`docs/investigation/README.md`](../investigation/README.md)). Each stands until the implementation proves it wrong.

- **Rows on the wire, not actions.** Clients compute row writes (put, patch, delete) from their store rules and sync those. The server applies rows with no app logic. An action log was rejected because it needs identical reducers in TypeScript and Swift, action shapes that can never be removed, and a full replay on schema changes. An append-only `_log` of applied row writes next to the mirror covers activity feeds and debugging.
- **One Durable Object with SQLite storage per space.** The object holds the app tables (the mirror), `_changes` (latest sequence per row), `_clients` (last acked sequence per client) and `_log`. Writes are serialized by the object, so there are no locks. An object is created on first use, so environments need no provisioning. Single-owner apps have one space; procrastimate has one per user and clients subscribe to the spaces they can see.
- **Conflicts: column-level last write to arrive.** Delete beats a later patch, a patch to a missing row is a no-op, a rejected write is dropped and the next pull restores the server's row. Both apps accept these rules today under PowerSync.
- **One round trip, Replicache-shaped.** `POST /sync {clientId, cursor, writes}` replays writes exactly once by per-client sequence number and returns the rows changed since the cursor. A cursor behind the compaction horizon gets a snapshot. A hibernating WebSocket carries only `{cursor}` nudges.
- **Tombstones and the log expire behind a horizon.** `_changes` and `_log` grew forever in protocol 1. A space now keeps `_meta.horizon`: at the end of a sync, when `compactEvery` (default one hour) has passed since `compacted_at`, the horizon moves to the last `_log` seq older than `retention` (default 30 days), and tombstones and log rows at or below it are deleted. Live `_changes` rows stay, since delta pulls need them. A cursor below the horizon cannot be served a complete delta, so it gets a snapshot exactly like cursor 0; a cursor at the horizon has seen every dropped tombstone and gets a delta. A client that is offline longer than the retention pays one snapshot, which is the trade we want: the common case stays a delta and the server stays bounded. `compact()` is exposed for tools and tests, and the clock is injectable so tests drive it.
- **Snapshots are paged, and the page cursor is a row key, not an offset.** Protocol 2 returns a snapshot in pages of `pageSize` rows (default 1000) ordered by schema table order then id, each with `next: {table, id} | null`. A key cursor survives writes that land between pages; an offset would skip or repeat rows after a delete. The client wipes local tables only on a page it requested without `after`, keeps `_meta.after` and `_meta.snapshot_head` as the one record that a snapshot is in progress, and sets `_meta.cursor` to the first page's head when the last page lands, so rows that changed between pages come with the next delta instead of being missed. A crash between pages resumes from `_meta.after` without a second wipe. `SyncStatus.snapshot` reports the rows applied so far so a UI can show the first download.
- **Protocol 1 stays accepted for one release, unpaged.** a-better-me's phone has no update channel and runs the v1 client until the owner installs a build. A v1 client ignores `next` and would lose the rows of later pages, so a v1 request gets the whole snapshot in one response and no `next` key, as before. Remove protocol 1 (the `protocol: 1` branch in `SyncRequest`, `SyncRequestSchema` and `createSpace`'s unpaged path) once the owner's phone runs a protocol 2 build; the 426 then covers it like any other stale client.
- **The engine core runs anywhere SQLite runs.** It targets a small SQL driver interface. Durable Object storage is production, bun:sqlite runs tests and local tools, and D1 or libsql adapters are possible without touching the core.
- **Same DDL on client and server.** One Drizzle `sqlite-core` schema per app is the source of the DDL on both sides, and the Zod validators next to it are the only app logic the server runs. There is no schema hash and no shape version: a stale client is caught by the protocol version, and the schema itself only grows.
- **Web storage is sqlite-wasm with OPFS in one dedicated worker per tab, and the tabs elect a host.** One connection serves every tab, but it cannot live in a SharedWorker. Chromium exposes `createSyncAccessHandle` only to dedicated workers, and its SharedWorker scope has no `Worker` constructor, so a SharedWorker can neither open the database nor spawn a worker that does (measured 2026-10-24 with Playwright chromium-1248; webkit-2370 allows both). The host is whichever tab's worker holds the Web Lock `sync-engine:<filename>`, and the other workers forward their commands to it over a `BroadcastChannel` of the same name. See [Web client](#web-client). This is the one client piece PowerSync provided that we must write ourselves.

## Packaging

- **One repo, one package, versioned together.** The repo is the single package `sync-engine`, and each TypeScript package under `packages/` is a subpath export (`sync-engine/core`, `sync-engine/client`, `sync-engine/bun-sqlite`, `sync-engine/bun-server`, `sync-engine/cloudflare`, `sync-engine/schema`) that points at its `src/index.ts`. Apps install it from a git ref, `"sync-engine": "github:smirea/sync-engine#<sha>"`, and nothing goes to npm: there is no npm account, and a git dependency does not link workspaces, so separate packages could not be consumed. Packages import each other by relative path to `src/index.ts`, never by name or tsconfig alias, so an installed copy resolves with no install or build step of its own. `files` ships only `packages/*/src`, `Package.swift` and `Sources`. A `Package.swift` at the repo root serves SwiftPM from the same ref. One ref moves every client and the server at once, and the wire protocol carries a version so a stale client resets instead of misbehaving. No backwards compatibility between versions.
- **The app owns its schema, the package owns everything derived from it.** An app's `sync.config.ts` exports Drizzle `sqlite-core` tables plus, per JSON or enum column, a Zod schema for the value (procrastimate's `COLUMN_VALUES` pattern). The package exports `defineSchema` to type that and nothing else about the app.
- **TypeScript needs no generated types.** Row types come from Drizzle's inference, validators from Zod. The one generator is `generate()` from `sync-engine/schema`, called by the app's own script: it writes `SyncSchema.swift`, which holds the table list with each table's columns and the client DDL statements in order, and optionally the same DDL as a `.sql` file. The app commits the output and keeps a test that regenerates it and fails when the committed file is stale, so a schema change cannot ship half-propagated. Swift structs stay hand-written in the app; the package generates no structs and no GRDB conformances.
- **Migrations are additive and computed from the live database.** On start, server and client each compare `PRAGMA table_info` with the schema and run `CREATE TABLE IF NOT EXISTS` and `ALTER TABLE ... ADD COLUMN` for what they lack; there is no snapshot file, no migration history and no check command. A removed column stays in place and is ignored, and a column whose type must change gets a new name. A client database is never dropped for a schema change.
- **Packages.** `core` is the whole protocol over a `SqlDriver` with `exec` and `transaction`, no I/O: `defineSchema`, the DDL and additive migration, `createSpace` (server apply and pull), `createClient` (outbox coalescing and client apply), and `handleSync`, the one HTTP boundary every server shares. Both sides live in one package because they share the schema, the column validation and the upsert, and because the conformance test exercises them together. `bun-sqlite` is the driver over bun:sqlite for tests, tools and the Bun server. `bun-server` and `cloudflare` are transports: a Bun HTTP server for local runs, and a Durable Object base class plus a Worker helper that takes the app's auth and space resolution as functions. `client` is the sync loop over a transport: push, pull, live updates and change notifications. `schema` is the generator as one function the app's own scripts call: `generate({ schema, swift?, ddl? })` returns and optionally writes `SyncSchema.swift` and the client DDL, both from core's `clientStatements`, so the SQL is rendered in one place. `client-web` is the browser client in two entry points: `sync-engine/client-web/worker` runs the database and the sync loop inside the app's worker script, and `sync-engine/client-web` is the main-thread handle plus a drizzle adapter over `drizzle-orm/sqlite-proxy`. The Swift package mirrors the client half of `core` over GRDB. App-specific generators such as procrastimate's OpenAPI and Swift API types stay in the app.
- **Authorization is the app's, on both routes.** Servers take `authorize(request)` and run it before `/sync` and `/live`; a false answer is 401. The client sends `Authorization: Bearer` on the POST. Browsers cannot set WebSocket headers, so it sends the token as a `bearer.<token>` subprotocol next to `sync-engine.v1`, which the server echoes, and `bearerToken(request)` in core reads either place.

## Client loop and local server

- **One sync at a time, waiters coalesce.** `createSyncClient` models its run as idle, running, or running with one queued run. A `sync()` during a run joins the single queued run, which collects the outbox only when it starts, so any number of triggers cost at most one extra round trip. `onChange` listeners run after the run settles, so they read a finished status.
- **Every trigger is a sync.** Socket open, a `{"head": N}` nudge above the cursor, a `markDirty()` after a 100 ms trailing throttle, the periodic timer, and the browser `online` event all call the same serialized `sync()`. A sync on every open covers nudges lost while disconnected. A failed sync retries with exponential backoff from 1 s capped at 15 s; `markDirty()` cancels a pending retry so the write goes out after the 100 ms throttle instead, and the `online` and `visibilitychange` events reset both backoffs and sync at once. The Swift client does the same on a satisfied `NWPathMonitor` path and on foreground, so an outage costs at most 15 s per side instead of 60.
- **The live socket checks itself.** The client sends `ping` every 30 s and the server answers `pong`; a socket that heard nothing since the previous ping is dropped and reconnected, since a dead TCP connection may never report a close. Reconnects back off from 1 s, doubling to 15 s, reset by a successful open; `maxBackoff` lowers that cap for reconnects and retries alike.
- **`/live` takes the token as a header or a subprotocol.** The Swift client sends `Authorization: Bearer`, the browser sends `bearer.<token>`, and `authorize` always reads the header because the server passes it `withBearer(request)`. The server echoes `sync-engine.v1` only when the client offered it: a client that offered no subprotocol fails the handshake on an echo (Bun reports "Mismatch client protocol"). A subprotocol token must use token characters, so base64url or a JWT works and standard base64, whose `/` and `=` are not allowed, does not.
- **`bun-server` is the local dev server.** `serve()` runs one space over one SQLite file (or an injected driver) behind the app's `authorize` function, publishes `{"head": N}` to every socket when a sync advanced the head, and answers 404 for anything but `POST /sync` and `GET /live`. It answers the CORS preflight for `/sync` and allows any origin, so a dev server on another port (Vite, the web test page) can call it without a proxy. Production servers sit behind the app's own origin or proxy.

## Web client

- **One dedicated worker per tab, one host.** The app bundles a worker script that calls `startSyncWorker({ schema, endpoint, filename, token? })`, and each tab opens it with `new Worker(url, { type: 'module' })` and wraps it with `openSyncDatabase({ worker })`. Every worker requests the Web Lock `sync-engine:<filename>`; the holder is the host, opens the database, runs `createSyncClient`, and serves the others, which stay in the lock queue as peers and forward every command over a `BroadcastChannel` of the same name. Replies and change notifications travel back the same way. A tab's own worker settles `setToken` and `close` itself and broadcasts the token so every worker holds the current one.
- **Failover is the lock queue.** When the host's tab closes, the browser releases its lock and the next worker becomes host. It retries `installOpfsSAHPoolVfs` for up to 3 s because the dead worker's access handles are released a moment after it dies (Chromium reports `NoModificationAllowedError`, WebKit `InvalidStateError`), announces itself on the bus, and the peers resend what they still have in flight. Measured close-to-next-write time was 36 ms in chromium and 45 ms in webkit. The one hole: a write the old host executed but never answered is resent and can fail on its primary key. The pool is opened with `preserveOnInitFailure`, because the default on a failed open removes the pool directory, which is another worker's live database.
- **opfs-sahpool, no COOP/COEP.** The `opfs-sahpool` VFS "does not require COOP/COEP HTTP headers" ([sqlite.org/wasm persistence](https://sqlite.org/wasm/doc/trunk/persistence.md)), and the web test serves its page with plain headers. A pool allows one connection per directory, so the pool name and directory derive from the filename and two filenames never share a host. The `already-open` error is reachable only without Web Locks, when a second worker opens the same pool directly.
- **No explicit transactions, `batch` is the transactional form.** The connection is shared, so a `BEGIN` from one tab would swallow another tab's statements. After every `exec`, on success and on error, the worker checks `sqlite3_get_autocommit` and rolls back a transaction left open, so a `BEGIN; INSERT ...` that fails midway cannot swallow another tab's next write; a statement that left one open on success is answered with `explicit-transaction`. `batch([...])` runs its statements in one transaction and is what the drizzle adapter's `db.batch()` maps to; drizzle's `db.transaction()` sends a bare `BEGIN` and gets that error.
- **Local writes notify every tab.** An `sqlite3_update_hook` collects the tables each `exec` or `batch` touched. App tables call `markDirty()` so the write syncs after the 100 ms throttle, and every touched table that is not internal goes out as one `change` to this tab and over the bus to the others. Pulled rows notify through the client's `onChange` the same way. A tab also hears the echo of its own write when the next pull applies the server's copy. Measured write-to-other-tab latency, taken in page clocks from before the drizzle insert to the other tab's `onChange`: 7 ms in chromium, 1 ms in webkit. A worker that is still loading its script misses a notification sent meanwhile; its first query reads the current rows anyway.
- **Token model.** `token` undefined starts the loop with no auth, a string starts it with that token, `null` keeps the loop stopped until `setToken(string)`, and `setToken(null)` stops it again. Local reads and writes work in every state. `createSyncClient` reads the token on each request, so the worker mutates its options and restarts the live socket. A worker announces its own string token when it starts and otherwise sends `hello`, which the host answers with the current token, so a tab that joins after a `setToken` holds the same state and keeps the loop running if it becomes host.
- **WebKit needs a persistent context.** In a Playwright ephemeral context every OPFS call in WebKit fails with `UnknownError`, so the web test uses `launchPersistentContext` for both browsers. Chromium works in either. Both browsers behaved the same on every other point the test covers.

## Specification and conformance

- **`spec/` holds the protocol as Bend.** `spec/sync.bend` is the pure model of server state, `apply`, `applyBatch`, `compact`, `pull`, `pullPage`, the client's `applyPull` and the outbox's `collect`. `spec/LAWS.bend` is human-owned and states the invariants: replay idempotence, head monotonicity, convergence after a pull, preservation of the convergence invariant under `apply`, compaction preserving rows and head, convergence for every cursor once compaction exists (snapshot path below the horizon, delta path above), batch order (an adjacent swap of two distinct seqs in the arrival order changes nothing, the law that would have caught the PR 7 finding where `[3, 2]` skipped seq 2) and batch completeness (an ascending batch above `clients[c]` passes the replay guard on every write and leaves `clients[c]` at the last seq; with batch order this covers any arrival order). `spec/PROOF.bend` holds the proofs, which agents maintain. An agent that changes the protocol edits the model, re-aligns the proofs, and never weakens a law. CI runs `bend PROOF.bend`.
- **Paging convergence is not a law.** The claim that a client applying pages from successive states and then one delta from the first page's head equals the final state needs the key order's totality and a page-by-page induction over a changing state; that proof did not fit a reasonable effort, so it stays out of `LAWS.bend`. It is covered by the model's `pullPage` in every vector scenario (pages of three while writes land, then a delta) and by the `pageSize`-2 core test with a write and a crash between pages. The `Asc` predicate in the model is a `Bool` rather than a `Type` so that a law's hypothesis is a copyable equality.
- **The TypeScript core is tested against the model.** `bun run spec-vectors` (`scripts/spec-vectors.ts`) builds the model with `bend spec/sync.bend -o spec/sync.mjs`, drives 20 seeded scenarios of 30 writes through it and writes `spec/vectors.json` with the model state after every write, pulls at three cursors, one `applyPull`, a compaction at write 20 with pulls below, at and above the horizon, an outbox of local edits through `collect` and one batch, and pages of three rows taken while writes land followed by a delta. `packages/core/spec.test.ts` replays every vector through the core on bun:sqlite and compares rows, head, changes and client seqs. The file carries the sha256 of `spec/sync.bend`, and the test fails on a mismatch, so a model change cannot ship with stale vectors and CI needs no Bend for the comparison. Where the prose and the model disagreed, the model won: a delete of a missing row counts and writes a tombstone, and an empty patch on an existing row counts. The Swift client applies rows and keeps an outbox, so it is covered by the same vectors through its `applyPull`.
- **The model stays small and stable.** It covers the protocol, not app schemas. Columns and values are opaque naturals in the model. A schema change in an app never touches `spec/`.
