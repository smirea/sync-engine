# Sync

Decisions from the 2026-10-24 investigation ([`docs/investigation/README.md`](../investigation/README.md)). Each stands until the implementation proves it wrong.

- **Rows on the wire, not actions.** Clients compute row writes (put, patch, delete) from their store rules and sync those. The server applies rows with no app logic. An action log was rejected because it needs identical reducers in TypeScript and Swift, action shapes that can never be removed, and a full replay on schema changes. An append-only `_log` of applied row writes next to the mirror covers activity feeds and debugging.
- **One Durable Object with SQLite storage per space.** The object holds the app tables (the mirror), `_changes` (latest sequence per row), `_clients` (last acked sequence per client) and `_log`. Writes are serialized by the object, so there are no locks. An object is created on first use, so environments need no provisioning. Single-owner apps have one space; procrastimate has one per user and clients subscribe to the spaces they can see.
- **Conflicts: column-level last write to arrive.** Delete beats a later patch, a patch to a missing row is a no-op, a rejected write is dropped and the next pull restores the server's row. Both apps accept these rules today under PowerSync.
- **One round trip, Replicache-shaped.** `POST /sync {clientId, cursor, writes}` replays writes exactly once by per-client sequence number and returns the rows changed since the cursor. A cursor behind the compaction horizon gets a snapshot. A hibernating WebSocket carries only `{cursor}` nudges.
- **The engine core runs anywhere SQLite runs.** It targets a small SQL driver interface. Durable Object storage is production, bun:sqlite runs tests and local tools, and D1 or libsql adapters are possible without touching the core.
- **Same DDL on client and server.** One Drizzle `sqlite-core` schema per app generates the DDL and migrations, Zod validators, Swift structs with GRDB conformance, and a schema hash. Additive changes apply as `ALTER` on both sides; shape changes make the client push its outbox, drop its database and pull a snapshot.
- **Web storage is sqlite-wasm with OPFS in a SharedWorker.** One connection serves every tab. This is the one client piece PowerSync provided that we must write ourselves.

## Packaging

- **One repo, versioned together.** Bun workspaces publish the TypeScript packages to npm, and a `Package.swift` at the repo root serves SwiftPM from the same git tag. One tag moves every client and the server at once, and the wire protocol carries a version so a stale client resets instead of misbehaving. No backwards compatibility between versions.
- **The app owns its schema, the package owns everything derived from it.** An app's `sync.config.ts` exports Drizzle `sqlite-core` tables plus, per JSON or enum column, a Zod schema for the value (procrastimate's `COLUMN_VALUES` pattern). The package exports `defineSchema` to type that and nothing else about the app.
- **TypeScript needs no generated types.** Row types come from Drizzle's inference, validators from Zod. The `sync-engine generate` command writes only what cannot be inferred: the SQLite DDL and additive migration steps, a schema hash, and the Swift file with the structs, GRDB conformances and the table list. Outputs land in the app's own `generated/` folders, git-ignored, regenerated by every start, test and build as both apps do today.
- **Migrations are diffs against a committed snapshot.** The generator keeps `schema.snapshot.json` in the app and appends additive steps when the schema grows. A change that drops or retypes a column bumps the shape version, and clients push their outbox, drop the local database and pull a snapshot. `sync-engine check` fails CI when any generated output or the snapshot is stale, so an agent's schema change cannot ship half-propagated.
- **Packages.** `core` is the whole protocol over a `SqlDriver` with `exec` and `transaction`, no I/O: `defineSchema`, the DDL and additive migration, `createSpace` (server apply and pull), `createClient` (outbox coalescing and client apply), and `handleSync`, the one HTTP boundary every server shares. Both sides live in one package because they share the schema, the column validation and the upsert, and because the conformance test exercises them together. `bun-sqlite` is the driver over bun:sqlite for tests, tools and the Bun server. `bun-server` and `cloudflare` are transports: a Bun HTTP server for local runs, and a Durable Object base class plus a Worker helper that takes the app's auth and space resolution as functions. `client` is the sync loop over a transport: push, pull, live updates and change notifications. `schema` is the generator as one function the app's own scripts call: `generate({ schema, swift?, ddl? })` returns and optionally writes `SyncSchema.swift` and the client DDL, both from core's `clientStatements`, so the SQL is rendered in one place. `client-web`, the sqlite-wasm OPFS SharedWorker driver, is not written yet. The Swift package mirrors the client half of `core` over GRDB. App-specific generators such as procrastimate's OpenAPI and Swift API types stay in the app.
- **Authorization is the app's, on both routes.** Servers take `authorize(request)` and run it before `/sync` and `/live`; a false answer is 401. The client sends `Authorization: Bearer` on the POST. Browsers cannot set WebSocket headers, so it sends the token as a `bearer.<token>` subprotocol next to `sync-engine.v1`, which the server echoes, and `bearerToken(request)` in core reads either place.

## Client loop and local server

- **One sync at a time, waiters coalesce.** `createSyncClient` models its run as idle, running, or running with one queued run. A `sync()` during a run joins the single queued run, which collects the outbox only when it starts, so any number of triggers cost at most one extra round trip. `onChange` listeners run after the run settles, so they read a finished status.
- **Every trigger is a sync.** Socket open, a `{"head": N}` nudge above the cursor, a `markDirty()` after a 100 ms trailing throttle, the periodic timer, and the browser `online` event all call the same serialized `sync()`. A sync on every open covers nudges lost while disconnected.
- **The live socket checks itself.** The client sends `ping` every 30 s and the server answers `pong`; a socket that heard nothing since the previous ping is dropped and reconnected, since a dead TCP connection may never report a close. Reconnects back off from 1 s, doubling to 60 s, reset by a successful open.
- **`/live` takes the token as a header or a subprotocol.** The Swift client sends `Authorization: Bearer`, the browser sends `bearer.<token>`, and `authorize` always reads the header because the server passes it `withBearer(request)`. The server echoes `sync-engine.v1` only when the client offered it: a client that offered no subprotocol fails the handshake on an echo (Bun reports "Mismatch client protocol"). A subprotocol token must use token characters, so base64url or a JWT works and standard base64, whose `/` and `=` are not allowed, does not.
- **`bun-server` is the local dev server.** `serve()` runs one space over one SQLite file (or an injected driver) behind the app's `authorize` function, publishes `{"head": N}` to every socket when a sync advanced the head, and answers 404 for anything but `POST /sync` and `GET /live`.

## Specification and conformance

- **`spec/` holds the protocol as Bend.** `spec/sync.bend` is the pure model of server state, `apply`, `pull` and the client's `applyPull`. `spec/LAWS.bend` is human-owned and states the invariants: replay idempotence, head monotonicity, convergence after a pull, and preservation of the convergence invariant under `apply`. `spec/PROOF.bend` holds the proofs, which agents maintain. An agent that changes the protocol edits the model, re-aligns the proofs, and never weakens a law. CI runs `bend PROOF.bend`.
- **The TypeScript core is tested against the model.** `bun run spec-vectors` (`scripts/spec-vectors.ts`) builds the model with `bend spec/sync.bend -o spec/sync.mjs`, drives 20 seeded scenarios of 30 writes through it and writes `spec/vectors.json` with the model state after every write, pulls at three cursors and one `applyPull`. `packages/core/spec.test.ts` replays every vector through the core on bun:sqlite and compares rows, head, changes and client seqs. The file carries the sha256 of `spec/sync.bend`, and the test fails on a mismatch, so a model change cannot ship with stale vectors and CI needs no Bend for the comparison. Where the prose and the model disagreed, the model won: a delete of a missing row counts and writes a tombstone, and an empty patch on an existing row counts. The Swift client applies rows and keeps an outbox, so it is covered by the same vectors through its `applyPull`.
- **The model stays small and stable.** It covers the protocol, not app schemas. Columns and values are opaque naturals in the model. A schema change in an app never touches `spec/`.
