# Workflow

- **One PR per thread, never stacked.** Fold small same-area follow-ups into an open PR instead of starting a new thread.
- **Rebase only on a real conflict.** PR CI already tests the merge with `master`.
- **PRs wait on one script.** `pr-ship [--merge]`, shared from `~/code/scripts`, waits for CI, lists failing checks and unresolved review threads, reports a conflict with the base branch, and merges when green. It exits before the 600-second tool limit with a code that names the next step, printed as its last line, so an agent reruns it instead of writing `sleep` loops. A main T3 thread doesn't loop it: T3's `watch_pull_request` wakes the thread on checks, comments and conflicts, and `pr-ship --once --merge` gives the verdict on each wake. Delegated children can't watch a PR, so they keep the loop.
- **Hooks install with `bun install`.** Bun skips dependency lifecycle scripts, so lefthook's own installer never runs; the root `postinstall` runs `lefthook install` when the checkout is a git repository.
- **Pre-commit runs every check for each stack the commit touches; nothing runs at pre-push.** Lefthook runs its jobs in parallel, each behind a glob for its stack. `fix` runs oxlint on the staged script files. `typecheck` runs `bun run typecheck` over the project when a script or JSON file is staged. `test` runs the whole `bun run test` suite (about 0.2 s), not a selection by import graph, since that saved nothing and missed tests whose input is a data file such as `spec/vectors.json`. `swift` runs `swift test` when `Package.swift`, `Sources/` or `Tests/` is staged (about 2.5 s warm; the first build after a clean `.build` takes about 90 s). `spec` is described below. Test jobs unset git's hook variables first (`unset $(git rev-parse --local-env-vars)`), so a test that runs git in a temp directory cannot act on this repository. No hook starts a browser, a simulator or a server. Formatting is not enforced.
- **Tests run in a pinned zone and never against a remote database.** `bunfig.toml` preloads `scripts/test-timezone.ts` and `scripts/test-guard.ts`.
- **Git hooks are never skipped.** A Claude Code hook in `.claude/settings.json` blocks `--no-verify` and lefthook overrides. A failing hook gets its cause fixed; a flaky test is a bad test.
- **Run only the relevant tests locally.** CI runs the full suite.
- **A merge here is not done until its consumers pin it.** Consumers track `master` and the lockfile pins the commit, and nothing bumps it, so a fix stays out of production until someone does. After every merge to `master` that changes shipped code, move the pin to the merge commit in each repo that depends on the engine: `bun update sync-engine` for `bun.lock`, and the revision in the Swift `Package.resolved`. Today that is `a-better-me`. Find others with `grep -rl smirea/sync-engine ~/code --include=package.json --include=Package.resolved`. This package gets features and fixes far more often than it breaks, so the bump is committed straight to the consumer's `master` with its hooks run, after its relevant tests and `xcodebuild -resolvePackageDependencies` pass. A merge that breaks the wire protocol, an exported API or a table schema consumers use is the exception: that bump goes through a PR with the migration it needs, shipped with the consumer's own script. A docs-only merge needs no bump.
- **The protocol proofs run under the Lean kernel.** `bun run spec` runs `bend spec/PROOF.bend --verdict` with the Bend release and Lean toolchain pinned in `spec/toolchain.json`; `--install` fetches both into `~/.bend` and `~/.elan` without touching a shell profile. Pre-commit runs it when a `spec/` file is staged, and the CI `proofs` job runs it with `--install` when `spec/` or `scripts/spec.ts` changed, caching the two toolchains by the pin file's hash. A failing proof is fixed by re-aligning `PROOF.bend`, never by weakening `LAWS.bend`.
- **Tests state a rule and run in-process.** The `tests` skill sets the bar: a test is named as the rule it states and runs in milliseconds with no browser, server, port, network, real clock or sleep. The TypeScript client's tests answer its `fetch` with `handleSync` over an in-memory space and drive its timers with `jest.useFakeTimers()`; the Swift client's answer through a scripted `URLProtocol`. Wiring, such as `bun-server`'s routes and the Cloudflare Worker, gets no test: it is verified by running it, the Worker through `packages/cloudflare/example/smoke.ts`.
- **The browser suite is the one exception, and runs only in CI.** `packages/client-web/web.test.ts` covers sync logic that has no runtime but a page, a worker and OPFS, through the page's API and never its UI. `bun run test` ignores `packages/client-web`, so the hook never runs it, and `bun run test:web` runs it; it needs `bunx playwright install chromium webkit` once per machine and fails with that command when a browser is missing. Each case starts its own server and its own OPFS file, since WebKit keeps OPFS across persistent contexts. The CI `web` job installs the browsers and runs it when `packages/client-web`, `client`, `core`, `bun-sqlite` or `bun-server` changed.
- **The protocol vectors are checked against the model by `bun run spec`.** `scripts/spec.ts` fails before the proofs when `spec/vectors.json` was generated from another `spec/sync.bend`, so a stale contract is caught where the model changes.
- **CI runs one job per check, in parallel.** The `bun` matrix runs `lint:ci`, `typecheck`, `test` and `build` as four jobs on every change, with no change detection in front of them, since a detection job would delay each by about as long as the check itself takes; each times out at 5 minutes. The `changes` job gates only the jobs whose setup is expensive: `swift`, `web` (browser install) and `proofs` (Bend and Lean toolchains). Each of those reports success without running when its inputs did not change.
- **Swift tests run on macOS in CI.** `.github/scripts/changes.ts` names `Package.swift`, `Sources/` and `Tests/` as Swift paths. The `swift` job runs `swift test` on the newest macOS runner when one of them changed, and otherwise reports success from a Linux runner, so a change that touches no Swift never waits for a macOS machine. The package's tests need no simulator, server or Bun.
