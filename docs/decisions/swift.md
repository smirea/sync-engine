# Swift client

The Swift client of the protocol in [`protocol.md`](../protocol.md), for iOS apps that keep their data in GRDB.

- **One SwiftPM package at the repository root.** `Package.swift` declares the `SyncEngine` library with sources in `Sources/SyncEngine` and tests in `Tests/SyncEngineTests`, next to the TypeScript workspaces. An app depends on the same git tag that publishes the TypeScript packages: `.package(url: "https://github.com/smirea/sync-engine", exact: "<tag>")`, or `branch: "master"` while nothing is tagged. The package declares iOS 27 and macOS 26 so `swift test` runs on a Mac without a simulator.
- **GRDB is the only dependency.** The app already opens its `DatabasePool` through GRDB and its models are GRDB records; the client takes that pool and adds nothing on top of it. Screens keep observing with `ValueObservation`, and the app keeps writing through GRDB. The generated triggers capture every write, so the client has no write API.
- **The app passes the generated `SyncSchema`.** `tables` names each table's columns besides `id`, and `statements` is the complete client DDL in order. `migrate()` runs the statements, skips an `ALTER TABLE ... ADD COLUMN` the table already has, then throws when a schema column is missing from the database. The generator emits the `ALTER TABLE` for a grown schema; the client cannot, because `SyncTable` carries no column types.
- **Store and client are separate.** `SyncStore` is the protocol's SQL over one `Database`: `migrate`, `collect` (coalescing the outbox) and `apply`. `SyncClient` is a `@MainActor @Observable` class that owns networking, status, the live WebSocket and its triggers. Tests cover the store through a `DatabasePool` and the client through a `URLProtocol` stub, with no server.
- **The engine detects local writes by watching `_outbox`.** One `ValueObservation` reads the row count and the highest `seq`. The count is `pending`. A higher `seq` than the last seen schedules a sync 100 ms later, and writes inside that window share it; the apply's own deletions only lower the seq and schedule nothing.
- **Live updates and retries run while started, in the foreground, and not refused.** Three facts (`running`, `foreground`, `authorized`) decide whether the WebSocket and the 60-second periodic pull run, and nothing schedules a sync unless the client is running and authorized. A 401 clears `authorized`; only the public `sync()` sets it back, so a bad token costs one request, and a local write, a trigger or a retry never re-sends it. A URL error is `.offline`, any other non-200 status is `.failed("HTTP <code>")`, and both retry with exponential backoff capped at 60 seconds. A `SyncSchemaError` (a blob, an outbox row for an unknown table) is `.failed` with no retry and an `assertionFailure`, because it is a programming error. Foreground, background and a regained network path each trigger a sync; the background one holds a UIKit background task assertion.
- **The socket pings every 30 seconds and counts a pong as connected.** Idle NAT and proxy timeouts would otherwise drop it, and a connection that drops before any message would otherwise grow the reconnect backoff. The server also tells the writer about its own `head`, usually before the response is applied, so a head seen during a sync is checked again after it instead of pulled at once.
- **Loops hold the client weakly.** The WebSocket loop, the periodic pull and the lifecycle triggers capture `self` weakly and re-check it each iteration, and an isolated `deinit` calls `stop()`, so a client dropped without `stop()` releases its socket and timers.
- **A put or patch whose local row is gone is dropped.** The outbox stores no values, so a row deleted while `applying` was set has nothing to send. `collect` reports the highest outbox seq it read, sent or dropped, and the client clears outbox rows up to the larger of that and the server's `acked`.
- **An ack above the largest seq sent means a shared client id.** A restored backup or a copied database replays sequences the server already saw and would have its new writes silently dropped. The client mints a new `_meta.client`, keeps the outbox, discards the response and re-sends under the new id.
- **`rejected` keeps the last 20 refusals, newest first.** The server drops a rejected write and the client never resends it, so the property is the only trace a Sync screen can show.
